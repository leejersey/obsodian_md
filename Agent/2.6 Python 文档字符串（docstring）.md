### **Python 文档字符串（docstring）详解：docstring 是写在函数、类或模块开头的说明性字符串——它不是普通注释，而是能被程序读取、被 `help()` 调用、被 IDE 展示的"官方说明书"，是让代码自我解释、团队协作顺畅、AI 应用可维护的重要习惯**

上一节我们用类型注解让函数签名"说清了传什么、返回什么"。但注解只能表达类型，无法说明**"这个函数到底做什么、参数代表什么业务含义、什么情况下会出错"**。这些就是文档字符串（docstring）的职责。docstring 是函数模块的收尾内容，也是把前面所有知识串成"专业代码"的最后一块拼图。它看似只是"写几句说明"，但用好它能让你的代码从"能跑"变成"好懂、好用、好维护"。本节会讲清 docstring 与普通注释的本质区别、书写规范、几种主流风格，以及它在 AI 开发中的实际价值。

### **一、什么是 docstring：能被程序读取的说明**

docstring 是**紧跟在函数、类或模块定义第一行之后的字符串字面量**，通常用三引号 `"""..."""` 包裹。它用来说明这段代码"是做什么的"。

```python
def greet(name):
    """向指定的人打招呼并返回问候语。"""
    return f"你好，{name}"
```

那个三引号字符串就是 docstring。它看起来像一句话，但它有一个普通注释绝不具备的特性——**它会被 Python 存储起来，可以在程序运行时被读取**：

```python
print(greet.__doc__)        # 向指定的人打招呼并返回问候语。
help(greet)                 # 显示函数的完整帮助信息
```

`greet.__doc__` 这个特殊属性保存了 docstring 的内容，而内置的 `help()` 函数正是靠读取 docstring 来生成帮助文档的。你平时用 `help(print)`、`help(list)` 看到的说明，本质上就是这些内置对象的 docstring。

### **二、docstring 与普通注释（#）的本质区别**

这是理解 docstring 定位的关键。很多初学者以为它就是"换了种写法的注释"，其实两者用途完全不同：

| 对比项 | 注释（`#`） | 文档字符串（docstring） |
|--------|-------------|------------------------|
| 写法 | `# 说明文字` | 三引号字符串 `"""..."""` |
| 位置 | 代码任意位置 | 函数/类/模块定义的**第一行之后** |
| 面向对象 | 给"阅读源码的人"看 | 给"使用这个函数的人"看 |
| 能否被程序读取 | **不能**，运行时被忽略 | **能**，存于 `__doc__`，可被 `help()` 读取 |
| 典型用途 | 解释"这行代码怎么实现的" | 说明"这个函数是干什么、怎么用的" |

一句话概括：**注释解释"实现细节（怎么做）"，docstring 说明"使用方式（做什么、怎么用）"。** 前者是给维护代码的人看的内部备注，后者是给调用代码的人看的外部接口说明。二者不是替代关系，而是各司其职。

```python
def calculate_discount(price, rate):
    """根据折扣率计算折后价格。"""      # docstring：对外说明
    # 折扣率转成小数再计算（这是内部实现细节）   # 注释：对内解释
    return price * (1 - rate / 100)
```

### **三、docstring 的基本规范**

Python 官方（PEP 257）对 docstring 有一套约定，遵循它能让你的文档专业且一致：

- **始终使用三引号** `"""`，即使只有一行。这样后续要扩展成多行时无需改动。
- **紧跟在定义行的下一行**，且与函数体保持相同缩进。
- **首字母大写，以句号结尾**，用完整的句子描述。
- **首行是简短摘要**，用一句话概括功能，最好是祈使句（"计算……""返回……""发送……"）。

#### **单行 docstring**

适合功能简单、一句话能说清的函数：

```python
def add(a, b):
    """返回两个数字的和。"""
    return a + b
```

#### **多行 docstring**

功能稍复杂时，用多行结构：**第一行是摘要，空一行，然后是详细说明**，最后的 `"""` 通常单独占一行。

```python
def calculate_bmi(weight, height):
    """计算身体质量指数（BMI）。

    根据体重和身高计算 BMI，用于评估体重是否健康。
    公式为：体重(kg) 除以 身高(m) 的平方。
    """
    return weight / (height ** 2)
```

### **四、主流的 docstring 风格**

当需要详细说明参数、返回值、异常时，社区形成了几种结构化风格。了解它们能帮你读懂不同项目的代码，也便于文档工具自动生成 API 文档。下面介绍最常见的三种。

#### **1. Google 风格（最流行、最易读，推荐）**

用 `Args:`、`Returns:`、`Raises:` 等清晰的段落组织，可读性最好，是目前最受欢迎的风格：

```python
def send_request(url, timeout=30, retries=3):
    """向指定 URL 发送请求并返回响应内容。

    Args:
        url: 目标接口的完整地址。
        timeout: 超时时间（秒），默认 30。
        retries: 失败后的重试次数，默认 3。

    Returns:
        返回解析后的响应字典。

    Raises:
        TimeoutError: 当所有重试都超时后抛出。
        ValueError: 当 url 格式不合法时抛出。
    """
    ...
```

#### **2. NumPy 风格（科学计算、数据领域常用）**

用下划线分隔线来划分区块，在数据科学、机器学习库中很常见：

```python
def normalize(data, method="minmax"):
    """对数据进行归一化处理。

    Parameters
    ----------
    data : list[float]
        待归一化的数值列表。
    method : str, optional
        归一化方法，默认 "minmax"。

    Returns
    -------
    list[float]
        归一化后的数据。
    """
    ...
```

#### **3. reStructuredText / Sphinx 风格**

用 `:param:`、`:return:` 标记，是 Python 官方文档工具 Sphinx 的默认格式，较为紧凑但可读性略逊：

```python
def greet(name, greeting="你好"):
    """生成一句问候语。

    :param name: 要问候的人的名字。
    :param greeting: 问候用语，默认"你好"。
    :return: 拼接好的问候字符串。
    """
    ...
```

**选哪种？** 对个人和大多数项目，**推荐 Google 风格**——它最直观、最易读、上手最快。重点是：**在一个项目里保持统一**，不要混用。

### **五、docstring 与类型注解的配合**

一个常见的疑问是：**有了类型注解，还需要在 docstring 里写类型吗？** 二者其实是绝佳搭档、各有分工：

- **类型注解**负责说明"是什么类型"（`str`、`int`、`list`），这部分交给注解即可，docstring 里不必重复。
- **docstring**负责说明"是什么含义、有什么约束、代表什么业务概念"——这是注解表达不了的。

所以在有类型注解的现代代码里，docstring 的 `Args` 部分应聚焦"语义说明"而非"类型重复"：

```python
def chat(prompt: str, temperature: float = 0.7) -> dict[str, str]:
    """调用大模型生成回复。

    Args:
        prompt: 发送给模型的提示词内容。
        temperature: 采样温度，取值 0~2，越高回复越随机、越有创造性。

    Returns:
        包含 'reply' 键的字典，值为模型返回的文本。
    """
    ...
```

注意 `temperature` 的说明——它没有重复"这是个 float"（注解已经说了），而是补充了"取值范围"和"越高越随机"这类**注解无法表达的关键信息**。这就是二者配合的精髓：**注解管类型，docstring 管含义。**

### **六、模块与类的 docstring**

docstring 不只用于函数，模块（整个 `.py` 文件）和类同样应该有：

```python
"""文本处理工具模块。

提供文本清洗、分词、统计等功能，供 AI 应用的预处理阶段使用。
"""      # ↑ 模块 docstring：写在文件最开头

class ChatBot:
    """一个简单的对话机器人。

    维护对话历史，并封装与大模型交互的逻辑。

    Attributes:
        name: 机器人的名字。
        history: 保存对话记录的列表。
    """

    def __init__(self, name: str):
        """初始化机器人，设置名字并创建空的历史记录。"""
        self.name = name
        self.history = []
```

模块 docstring 写在文件**第一行**，说明整个文件的用途；类 docstring 紧跟 `class` 定义行，说明这个类是什么、有哪些重要属性。这些都为你下一模块要学的"面向对象"提前铺垫。

### **七、AI 开发实战：docstring 的实际价值**

在真实的 AI 项目中，好的 docstring 能带来实实在在的好处。看这个封装了 RAG 检索逻辑的函数：

```python
def retrieve(query: str, top_k: int = 5, threshold: float = 0.7) -> list[dict]:
    """从向量数据库检索与查询最相关的文档片段。

    将 query 向量化后，在知识库中做相似度检索，返回相关度
    最高的若干片段，并过滤掉低于阈值的结果。

    Args:
        query: 用户的查询问题。
        top_k: 最多返回的片段数量，默认 5。
        threshold: 相似度阈值（0~1），低于此值的结果会被过滤，默认 0.7。

    Returns:
        片段字典的列表，每个字典含 'text'（文本）和 'score'（相似度分数），
        按分数从高到低排序。若无满足条件的结果，返回空列表。
    """
    ...
```

这个 docstring 的价值体现在：**团队成员无需读实现就能正确调用它**（知道 `threshold` 是 0~1、知道返回值按分数排序、知道可能返回空列表）；**IDE 会在你敲代码时把这些说明浮现出来**；**未来的你半年后回看，也能立刻想起当初的设计**。在多人协作、逻辑复杂的 AI 应用里，这种"代码即文档"的能力能极大降低沟通和维护成本。

### **八、几条实用建议**

- **公开的函数、类、模块都应该有 docstring**，这是专业代码的基本要求；纯内部的、一望即知的小函数可以酌情省略。
- **写"做什么"和"怎么用"，而不是"怎么实现"**。实现细节属于注释（`#`），docstring 面向使用者。
- **保持 docstring 与代码同步更新**。过时的文档比没有文档更危险，因为它会误导人。改了函数行为，记得同步改 docstring。
- **不必对私有辅助函数过度文档化**。文档也有成本，把精力放在对外接口上，投入产出比最高。

### **小结与练习建议**

本节的核心记忆点有三个：**docstring 是写在定义第一行之后的三引号字符串，能被 `__doc__` 和 `help()` 读取，这是它区别于普通注释（`#`）的本质**；**注释解释"怎么实现（对内）"、docstring 说明"做什么、怎么用（对外）"，二者分工不同**；以及 **推荐用 Google 风格（`Args`/`Returns`/`Raises`）并在项目内保持统一，且 docstring 应与类型注解配合——注解管类型、docstring 管语义**。

建议动手做一个综合练习来巩固：**回顾你在前面几节写过的函数（比如 `safe_divide`、`build_prompt`、`retrieve`），给它们补上完整的 Google 风格 docstring——首行写一句话摘要，然后用 `Args` 说明每个参数的业务含义（不重复类型）、`Returns` 说明返回内容、必要时用 `Raises` 说明可能抛出的异常；写完后用 `help(函数名)` 打印出来，看看生成的帮助文档是否清晰易懂。** 这个练习能让你真正体会到 docstring "代码即文档"的效果。
